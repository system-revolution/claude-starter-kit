## 緊急度の定義

| 緊急度 | 基準 | 対応 |
|--------|------|------|
| 高 | 業務停止レベル・データ損失の恐れ | 原因特定後、確認を簡略化して即修正可 |
| 中 | 業務に支障あり | 通常フロー（確認→修正） |
| 低 | 軽微な不具合・見た目の問題 | 次回リリースに含めてOK |

## Claude Codeへの指示

作業開始前に `.claude/skills/this-project/SKILL.md` を必ず読むこと。

### バグ修正の場合

1. CLAUDE.mdとdocs/を読み、プロジェクトの全体像を把握せよ
2. 報告内容を元にバグの原因を調査せよ
3. 以下を報告せよ：
   - **原因** — 何が原因でバグが発生しているか
   - **影響範囲** — 同じ原因で他にも壊れている箇所はないか
   - **修正方針** — どう直すか
   - **リスク** — 修正による副作用の可能性
4. 確認を取ってから、以下を実行して修正を開始せよ：
   ```bash
   git checkout -b fix/【バグ内容を簡潔に】
   git commit -m "WIP: 修正開始前のセーフポイント" --allow-empty
   ```
5. **Superpowersのred-green-refactorサイクルで修正せよ**
   - バグを再現するテストを書く → REDになることを確認 → 修正 → GREENになることを確認
6. テストが全て通過したらユーザーに報告し、マージ指示を待つ
7. プロジェクト固有の原因だった場合はCLAUDE.md学習ログに追記する（汎用的なパターンはECCが自動学習する）

### セキュリティ対応の場合

1. 脆弱性の内容を把握せよ
2. 影響範囲を特定せよ
3. 以下を報告せよ：
   - **脆弱性の内容と深刻度**
   - **影響を受けるデータ・機能**
   - **修正方針**
4. 確認を取ってから、以下を実行して修正を開始せよ：
   ```bash
   git checkout -b hotfix/【内容を簡潔に】
   git commit -m "WIP: 修正開始前のセーフポイント" --allow-empty
   ```
5. 同じ種類の脆弱性が他にないか横断的にチェック
6. テストが全て通過したらユーザーに報告し、マージ指示を待つ

### 依存パッケージ更新の場合

1. 現在のパッケージバージョンを確認せよ
2. 更新対象のライブラリがある場合は `use context7` で最新の破壊的変更・マイグレーションガイドを確認せよ
3. 以下を報告せよ：
   - **更新が必要なパッケージ一覧**（セキュリティ修正があるもの優先）
   - **破壊的変更の有無**
   - **更新手順**
4. 確認を取ってから、以下を実行して更新を開始せよ：
   ```bash
   git checkout -b fix/package-update
   git commit -m "WIP: 更新開始前のセーフポイント" --allow-empty
   ```
5. 更新後、ビルドが通ることを確認
6. 主要な機能が動作することを確認
7. テストが全て通過したらユーザーに報告し、マージ指示を待つ

### パフォーマンス改善の場合

1. 問題の箇所を特定せよ
2. 以下を報告せよ：
   - **ボトルネックの箇所**
   - **改善方針**（複数案あれば比較）
   - **期待される効果**
3. 確認を取ってから、以下を実行して改善を開始せよ：
   ```bash
   git checkout -b fix/performance-【箇所を簡潔に】
   git commit -m "WIP: 改善開始前のセーフポイント" --allow-empty
   ```
4. テストが全て通過したらユーザーに報告し、マージ指示を待つ

## 全種別共通のセキュリティチェック

報告前に必ずECCのdifferential-reviewスキルを使ってこのセッションのコード変更をセキュリティレビューせよ。
問題が検出された場合は修正してから報告に進むこと。

## 全種別共通の報告

作業完了後、以下を報告せよ：

1. 変更したファイルの一覧
2. 変更内容の要約
3. テスト結果（全て通過していること）
4. セキュリティチェック結果（問題なし or 修正内容）
5. ドキュメント更新の有無
6. 再発防止策（該当する場合）
7. クライアントへの報告文案（1〜3行）※修正内容の技術詳細は含めない。「対応済み」の事実のみ記載
8. 「テストが全て通過しセキュリティチェックが完了しました。確認をお願いします。マージ指示をお待ちしています」と報告する

## 注意事項

- 報告された問題だけを直す。「ついでにリファクタリング」は禁止
- 修正前に必ず原因を特定して報告する。闇雲に直さない
- mainには直接コミットしない。必ず fix/xxx または hotfix/xxx ブランチで作業する
- ユーザーの確認なしにmainへマージしない
- テストが全て通過していない状態でマージしない
- 緊急度が高い場合でも、確認なしに本番に影響する変更をしない
- セキュリティ関連の修正は、修正内容をクライアント報告に含めすぎない（攻撃手法の開示を防ぐ）
- 以下に該当する場合は作業を止め、ユーザーに確認せよ（feature-addテンプレートで再依頼が必要な可能性がある）：
  - 新規テーブルの追加が必要な場合
  - 影響ファイルが5つ以上になる場合
  - 既存の仕様変更を伴う場合
