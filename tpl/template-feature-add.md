## Claude Codeへの指示

以下の打ち合わせ議事録と私のディレクションを元に、機能追加・改修を実施せよ。
このプロジェクトには既にCLAUDE.mdとdocs/が存在する。

作業開始前に `.claude/skills/this-project/SKILL.md` を必ず読むこと。

### Step 1: 現状の把握

1. CLAUDE.mdとdocs/を読み、プロジェクトの全体像を把握せよ
2. 打ち合わせ議事録を読み、追加・改修の要件を整理せよ
3. 新しいライブラリを使う場合は `use context7` で最新Docを確認してから設計せよ
4. 以下を報告せよ：

- **変更の影響範囲** — どのファイル・テーブル・画面に影響するか
- **新規作成が必要なもの** — テーブル、コンポーネント、APIなど
- **既存コードの変更箇所** — どこをどう変えるか概要
- **リスク** — 既存機能を壊す可能性がある箇所
- **曖昧な点** — 判断が必要な点

報告後、以下を出力して停止せよ：

```
---WAITING FOR CONFIRMATION---
上記の内容を確認してください。「OK」の返答があるまでStep 2に進むことを禁止する。
```

### Step 2: 実装

確認が取れたら、以下を実行してから実装を開始せよ：

```bash
git checkout -b feature/【機能名】
git commit -m "WIP: 実装開始前のセーフポイント" --allow-empty
```

#### 実装ルール

- 独立した機能が複数ある場合は、ECCのAgent Teamsを使って並列で実装すること（共通ファイルを触る機能は直列で進めること）
- 並列実装の前に必ずインターフェースを確定させること
- 既存のコードパターン・命名規則に完全に合わせる
- CLAUDE.mdの作業プロトコルに従う
- TDDで進める。Superpowersのred-green-refactorサイクルに従う
- ライブラリのAPIを使う箇所では `use context7` で最新Docを確認してから書く
- DB変更がある場合はマイグレーションファイルを必ず作成する
- 1機能実装 → lint + typecheck + test → git commit → 次の機能の順で進める
- ビルドが通らない状態で次に進まない
- テストが全て通過するまでマージしない

### Step 3: ドキュメント更新（必須確認）

実装完了後、以下を確認し、変更があれば更新、なければ「更新不要」と明示して報告せよ：

- **docs/database.md** — テーブル追加・カラム追加があった場合
- **docs/api-endpoints.md** — エンドポイント追加があった場合
- **docs/features.md** — 機能追加・変更があった場合
- **CLAUDE.md** — 禁止事項やルールの追加が必要な場合

### Step 4: セキュリティチェック

ECCのdifferential-reviewスキルを使ってこのセッションのコード変更をセキュリティレビューせよ。
問題が検出された場合は修正してからStep 5に進むこと。

### Step 5: 報告

1. 変更したファイルの一覧
2. 追加・変更したテーブル
3. 追加・変更した画面
4. テスト結果（全て通過していること）
5. セキュリティチェック結果（問題なし or 修正内容）
6. 更新したドキュメントの一覧
7. 既存機能への影響の有無
8. 「テストが全て通過しセキュリティチェックが完了しました。確認をお願いします。マージ指示をお待ちしています」と報告する

## 注意事項

- 既存の CLAUDE.md、rules/、settings.json は基本的に変更しない
- 新しいルールが必要な場合のみ追記・追加する
- 「ついでにリファクタリング」は禁止。依頼された変更だけを行う
- 影響範囲が大きい場合は分割して段階的に実装する
- mainには直接コミットしない。必ず feature/xxx ブランチで作業する
- ユーザーの確認なしにmainへマージしない
- Step 1の確認（「OK」の返答）なしにStep 2に進まないこと。確認前に進んだ場合は即座に停止すること
- 以下に該当する場合は作業を止め、ユーザーに確認せよ（規模が想定より大きい可能性がある）：
  - 影響ファイルが10以上になる場合
  - 既存の仕様変更・破壊的変更を伴う場合
