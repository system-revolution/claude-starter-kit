# 自己改善スキル（プロジェクト固有版）

## ECC との役割分担

**ECC の Instinct 学習システム**がコーディングパターン全般を自動学習する。
このスキルは**プロジェクト固有の知見のみ**を CLAUDE.md に記録する役割に特化する。

| 記録先 | 担当 | 対象 |
|--------|------|------|
| `~/.claude/skills/learned/` | ECC（自動） | コーディングパターン全般・技術的な罠 |
| `CLAUDE.md 学習ログ` | このスキル | プロジェクト・クライアント固有の知見 |

## トリガータイミング

このスキルは **Stop フックからは自動呼び出しされない**。以下のタイミングで使う:

- ユーザーが明示的に呼んだとき（「学習ログに書いて」「これを記録して」）
- 作業完了時に Claude Code が自己判断で書くべきと判断したとき

## 判断基準（すべて Yes なら追記する）

1. **プロジェクト固有か？** — このプロジェクト・クライアント特有の話であるか
2. **パターン化できるか？** — 今回だけの話ではなく、今後も同じ状況が起きうるか
3. **構造的なミスか？** — 仕様の知識不足ではなく、やり方・手順・前提の誤りか
4. **既存ルールでカバーされていないか？** — CLAUDE.md、rules/、docs/ に既に書いてあるなら追記不要

## 追記するもの（例）

- このクライアント固有の業務ルール・判断基準を忘れた
- このプロジェクト固有の制約を忘れた（変更禁止ファイル、特殊なリポジトリ構成）
- クライアントが「それは違う」と言った設計判断でパターン化できるもの
- このプロジェクト特有の技術的な罠（他プロジェクトには当てはまらないもの）

## 追記しないもの（例）

- 汎用的なコーディングパターンのミス（→ ECC が自動学習する）
- 技術的な罠で他プロジェクトでも起きうるもの（→ ECC の Instinct に任せる）
- 単純な typo、変数名の間違い
- 仕様やデータの詳細（→ docs/ に書くべき）
- 1回きりの勘違い（再発の構造がない）
- ユーザーの好みの問題（「こっちのほうが好き」的な修正）

## 追記フォーマット

CLAUDE.md 末尾の「学習ログ」セクションに追記する:

```markdown
## 学習: [日付] [カテゴリ]
- 問題: [何を間違えたか — 1行]
- 対策: [次からどうするか — 具体的に Yes/No で判定できる形]
```

## ルール化の昇格

学習ログが10個を超えたら、ユーザーに提案する:

```
学習ログが10件を超えました。
以下の3件はルール化できそうです。.claude/rules/project/ に移動しますか？
- [ルール1]
- [ルール2]
- [ルール3]
```

## ベース昇格の判断

「他のプロジェクトでも使えそう」と判断した場合、ベースリポジトリへの昇格を提案する:

```
この学習ログはベースリポジトリ（claude-starter-kit）に昇格できそうです。
- 対象: [ルール内容]
- 昇格先案: .claude/rules/common/ または .claude/rules/stack/XXX.md
- 昇格しますか？
```

ベースへの昇格は `update-base` スキルの手順に従う。

## 重要

- ユーザーに「学習ログに書いていいですか？」と聞かない。自動で判断して書く
- 判断に迷ったら書かない（書きすぎよりマシ）
- 追記したら「学習ログに追記しました: [1行要約]」と報告する
- コーディングパターン全般のミスは ECC に任せ、二重記録しない
